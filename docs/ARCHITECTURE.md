# Kitesafari — общая картина и план (2026-11-07)

Как устроена система после grilling'а и двух исследований. Продуктовая часть — [PRODUCT_JTBD.md](PRODUCT_JTBD.md), пример дня — [BOT_DAY.md](BOT_DAY.md).

## Роли

| Что | Роль |
|---|---|
| **База (Supabase Postgres)** | Главная копия всего: туры, лодки, каюты, кто где живёт, вейтлист. Все записи — только сюда. |
| **Мини-апп** | Витрина для гостей: карта палуб, фото, описание сафари, бронь по приватной ссылке. Админка пока остаётся. |
| **Бот (Telegram, Claude)** | Приёмник всего входящего: форварды, текст, голос. Предлагает правку → после «ок» пишет в базу. Ведёт записную книжку (вейтлист, договорённости с датами). |
| **Google-таблица** | Витрина по ссылке: всегда текущая картина тура, обновляется сама. Плюс можно править прямо в ней (схема ниже). |

Кто может бронировать: старички сами (мини-апп, приватная ссылка), бот после «ок», админка. Все пути пишут в базу; две одновременные брони одной каюты невозможны (база проверяет и пишет одним действием — уже так работает в `create-booking`).

## Хранение данных

- **`cabins.guests` остаётся свободным текстом.** Всё, что делают с гостями (понять «Аня + Слава и ребёнок», переселить, ответить), делает модель. Ячейка в таблице = поле в базе один в один — на этом держится правка в таблице.
- **Строки «по гостю»** заводим только с приоритетом 2 (оплаты, паспорта, рейсы — факты, по которым код действует без модели). Тогда сразу с настоящими полями и разовым переносом текста.
- **`bookings` — не источник правды.** Считаем её журналом «кто бронировал через мини-апп» (Telegram, реквизиты плательщика). Ни на что не опираемся; если за весну не пригодится боту — удаляем.
- **Добавляем:** таблицу записной книжки бота (текст, необязательная дата, тур, открыто/закрыто) и журнал изменений кают (кто, когда, было → стало) — чтобы любую ошибку можно было найти и откатить.
- Имена гостей публично не читаются (миграция 008, функция `cabin-guests`).

## Правка прямо в Google-таблице

Таблица сама ничего не записывает. Правка = просьба, которую сервер применяет с проверкой.

**Устройство листа «Каюты»:** строка = каюта; видимая колонка «Кто живёт»; скрытая колонка **«исходник»** — текст, который сервер записал туда последний раз; служебная строка сверху с галочками **«Применить»** и **«Отменить мои правки»** и полем статуса.

**Подсветка без скриптов** (условное форматирование, настраивается сервером через API):
- жёлтая — видимый текст ≠ исходник (правка ещё не применена);
- красная — конфликт: каюта успела измениться в базе;
- оранжевая — сервер обновил каюту меньше чем за минуту до появления твоей правки («проверь»), применяется только вторым нажатием.

**Как применяется.** Сервер раз в 10 секунд читает лист (≈0,35–0,65 с на чтение; лимит Google — 300 запросов/мин, у нас 6). Увидел галочку «Применить» → по каждой жёлтой каюте сравнивает исходник с текущим значением в базе:
- совпадает → применяет, обновляет исходник;
- не совпадает → не применяет, красит красным, рядом пишет «в базе сейчас: …».
Связанные изменения (обмен) — всё или ничего. Результат пишется в поле статуса, галочка снимается. Промежуточные шаги (временная ячейка, Cmd+C/Cmd+V) не важны — сравнивается только итог на момент нажатия.

**Кто пишет в лист.** В каждый момент кто-то один:
- нет жёлтых строк → сервер обновляет лист после любых изменений в базе;
- есть жёлтые строки → сервер в лист не пишет, копит изменения и показывает их списком сверху («в базе 2 новых изменения: …, появятся после "Применить"»); после применения или отмены выкладывает накопленное.

**Оставшиеся риски:**
- первая правка за сессию в ту же полсекунды, что запись сервера → закрыто оранжевой подсветкой;
- забыл нажать «Применить» → витрина стоит; баннер в листе + напоминание в бот через 30 минут;
- ты и Олег правите лист руками одновременно → как обычный Google Docs (разные ячейки сводятся, в одной побеждает последний), кнопка общая; конфликтов с базой это не создаёт;
- сломана структура (удалена строка каюты, переставлены колонки, переименован лист) → сервер пишет «не понимаю таблицу» и ничего не применяет.

**Без Apps Script.** Вся логика на нашем сервере через Sheets API: галочка — встроенный флажок, подсветка — условное форматирование, опрос — по расписанию (Supabase Cron).

## Проверено (2026-11-07)

- **Скорость Sheets API** (с ноутбука): чтение листа 0,35 с, запись ячейки 0,40 с, «прочитать и записать» 0,82 с. Прошлые «1,5–2 с», скорее всего, от прокси через Apps Script (известные холодные старты).
- **Одновременная запись в Sheets**: 5/5 раз обе программы «победили», одна правка молча затёрта — в Sheets нет атомарного «проверь и запиши». Поэтому таблица не главная.
- **Подключение из Deno без библиотек** (WebCrypto: подпись токена сервисного аккаунта → чтение, запись, флажок + условное форматирование через batchUpdate) работает: токен 0,24 с, остальное 0,5–0,65 с. В самой среде Supabase Edge ещё не запускали — первый шаг реализации.
- **Расписание каждые 10 секунд**: Supabase Cron (pg_cron 1.6 доступен, не включён) поддерживает интервалы 1–59 секунд. Журнал запусков (`cron.job_run_details`) нужно чистить — 8640 записей в сутки.

## Исследования

- **Google-таблица как главная копия — известная ловушка:** нет атомарной записи; onEdit не срабатывает на записи через API, держит в очереди максимум 2 события, при вставке не даёт значений; люди ломают структуру сортировкой и вставкой колонок (даже Whalesync запрещает сортировать). Общий совет: у каждого поля один владелец, настоящая БД главная.
- **Табличные интерфейсы поверх Postgres:** лучший — NocoDB (живое подключение к Supabase, копирование диапазонов, роли). Минусы для нас: свой сервер или $48–60/мес, отдельный логин (та же беда, что с Notion), нет защиты «каюту только что заняли». Baserow/Grist/Teable/Airtable — только через копию. Держим NocoDB в запасе.
